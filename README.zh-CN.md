# Symbiqo — 采集系统设计档

> 这是一个**只有设计、没有实现**的公开仓库。
> 产品代码在私有仓库中，不对外提供。

Symbiqo 做一件事：把一个**只存在于网页界面里**的模型能力，变成标准 API
（OpenAI `/v1/chat/completions` 与 Anthropic `/v1/messages`）。

它不是抓页面。它是在真实浏览器会话里驱动界面、在网络层截取流式渲染、
再把增量输出重组成规范响应。这类系统与「发 HTTP 请求解析 HTML」的区别在于：
**你的对手是一个不断变化的前端状态机，而不是一份文档。**

## 这个仓库为什么存在

采集方向的工程能力，不体现在「爬过多少站」，体现在三件事：

1. **能不能度量自己**。成功率、分位时延、失败分类，得有口径、有分母、能证伪。
2. **能不能定位瓶颈归属**。失败是我方判据不准，还是对面在拦？两者优化路径完全不同。
3. **能不能划清边界**。哪些方法该写下来，哪些写下就等于失效，哪些不该写。

本仓库是这三件事的公开侧。**不含任何站点的接入方法、参数或规避手段**，
边界清单见 [`DISCLOSURE.md`](DISCLOSURE.zh-CN.md)。

## 三条结论

从这套系统里得到的判断，比代码本身更能说明问题：

**一、反爬不是主要成本。** 17.8 天里失败最多的不是被拦截，是「生成结束判定失效」
（76 条）与「页面结构变化未自愈」（67 条）。反爬拦截只占全部失败的 14.8%。
把预算先投在判据与自愈上，比投在对抗上收益高。

**二、成功率必须按目标拆分。** 同一套引擎跑六个目标，成功率从 94.0% 到 47.6%。
把六个数字平均成一个，等于把「我方实现缺陷」和「对方风控拦截」混成同一个数，
之后就再也无法判断该修什么。

**三、显式失败优于静默降级。** 某平台不支持附件，就声明能力缺失并拒绝请求，
而不是在渲染中途丢图。静默降级在采集系统里最贵——它不报错，只让数据悄悄变少。
